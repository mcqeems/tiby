# RapidOCR vs PaddleOCR for onboarding-card OCR

**Research snapshot: 18 October 2026.** This is a source-based selection note, not an accuracy benchmark. Application context: Python `>=3.10,<3.11`, CPU-first AI service; users photograph/upload Indonesian printed medication/treatment cards. OCR should draft name, regimen, quota, and dates for human review. The `/ocr/extract` route is not implemented and current backend OCR is a stub/fallback.

## Recommendation

Start with **RapidOCR v3 using ONNX Runtime CPU**, a pinned PP-OCRv6 `small` multilingual detector + recognizer route with `lang_type="id"`, and explicitly package/cache the selected model files as part of deployment. This best fits a lightweight local CPU service and avoids PaddlePaddle's framework/runtime installation path. The official RapidOCR model route explicitly lists Indonesian (`id`) for PP-OCRv6 small (also tiny/medium); it is a supported language route, not proof of accuracy on Indonesian treatment cards. PP-OCRv5's `latin` recognition model also supports Indonesian and has a published generic Latin-script dataset score; that score is not a card/photo benchmark. Use it as a fallback candidate to test, not as an assumed winner.

Keep **PaddleOCR** as a viable alternative if the team needs Paddle's upstream full pipeline/accuracy evaluation or prefers its broad ecosystem. It supports selecting lightweight mobile models, but its OCR package is a thin wrapper and the inference engine must be separately installed. A CPU-only ONNX Runtime path is documented, but adds PaddleOCR/PaddleX wrapper dependencies and model lifecycle work. Do not infer actual deployment size from the PyPI wrapper wheel size.

No primary source located publishes a direct RapidOCR-vs-PaddleOCR benchmark for the same runtime, Indonesian card images, or this field-extraction task. Before choosing on accuracy, collect a consented, de-identified set of representative photos and compare detection/recognition plus exact-field review rates. OCR only transcribes text; it does not reliably infer which number is quota, regimen, or date.

## Suggested evaluation/configuration

- Candidate A: RapidOCR `Rec` and `Det` ONNX Runtime, PP-OCRv6 `small`, language route `id`; include text-line orientation only if upside-down/rotated card photos justify its additional model/cost. Specify version, engine, size, and language explicitly rather than relying on changing defaults. Validate how RapidOCR v3.10's route config maps each component before implementation.
- Candidate B: PP-OCRv5 `latin` mobile recognizer + mobile detector, through RapidOCR or PaddleOCR. This is a purpose-built Latin-script route; compare against PP-OCRv6 Indonesian route using the same images. Don't confuse recognition language/model with detection model language.
- Candidate C: PaddleOCR 3.x `engine="onnxruntime"`, PP-OCRv5 mobile models, `lang="id"` (if current v3 route accepts it); verify the actual model selection in a smoke test. PaddleOCR docs' example uses `lang="en"`; the multilingual model reference establishes `id` for the v5 Latin recognizer.
- Evaluate detection misses, character error rate, and exact correctness of each draft field separately, stratified by blur/glare/skew, print size, handwritten marks, and card version. Preserve OCR boxes/confidence so users can compare text against the image. No automatic submission or medication instruction should be based solely on OCR.

## License and attribution

RapidOCR's **wrapper/code** is Apache-2.0, but RapidOCR's own model notice separately attributes upstream model weights to Baidu/PaddleOCR rights holders; its notice states the covered bundled/converted models are Apache-2.0 and requires Apache license and upstream notices/attribution on redistribution. It stresses that this notice only covers listed artifacts, not every model/runtime/asset. Check the exact chosen artifact's model card/registry and retain its provenance, revision and SHA-256 in deployment records. [RapidOCR model licensing](https://rapidai.github.io/RapidOCRDocs/latest/en/model_licenses/)

PaddleOCR **project code** is Apache-2.0. A model's license is a separate fact: inspect the exact official model card and retain applicable license/NOTICE/attribution when bundling weights. PaddleOCR's official model-list page gives model links and metrics; do not assume the package license alone establishes every third-party dependency/model's terms. [PaddleOCR repo](https://github.com/PaddlePaddle/PaddleOCR), [PaddleOCR model list](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/model_list.md)

## Operational and safety notes

- Treat card images and extracted names/regimens as sensitive health and identifying data. Prefer on-device/in-service OCR over external OCR APIs; avoid logging image bytes, OCR text, names, or full request bodies; set short retention/deletion bounds and access controls. Local inference avoids sending images to a third-party OCR service, but does not itself ensure privacy (uploads, logs, storage, backups, and observability still matter).
- Present the image alongside editable draft fields; require explicit human confirmation of name, regimen, quota, and dates. Low-confidence or conflicting/ambiguous values should remain blank/flagged, not guessed. Wrong medication directions/dates can cause harm.
- The OCR models are general text recognition, not medical understanding and not validated/certified for clinical decision-making. Neither published multilingual language coverage nor generic dataset accuracy guarantees performance on Indonesian treatment cards.
- Model downloads and package defaults are mutable supply-chain and availability surfaces. Pin package/runtime versions and model artifacts/hashes; pre-download in build/deployment, scan dependencies, and test startup/inference without outbound network. Budget for cold-start/model memory and prevent uncontrolled inference concurrency.
